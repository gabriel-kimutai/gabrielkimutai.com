## Overview

Heimdall is a systems project: a phone client and a computer daemon connected by a purpose-built protocol.

Install a small daemon on a computer, open Heimdall on Android, discover the machine on the LAN, pair once, then manage the host from the phone.

It is not a traditional remote desktop application. The goal is lightweight computer management — process control, system stats, power actions — with a native Android interface and a small agent on the host.

The Android application should not need to know how Linux performs a particular operation. It only needs to understand the Heimdall protocol. The daemon owns platform-specific work.

Heimdall is in active development. The architecture is organized around a stable foundation: discover a host, establish trust, then perform a small set of useful management operations.

## Problem

Managing a machine from a phone usually means either typing IP addresses and hoping DHCP does not move them, or pulling an entire desktop stream for actions that only need a few commands.

A phone is a good interface for questions such as:

- Is the computer running?
- How much CPU is it using?
- Is a process consuming too much memory?
- Restart the machine.
- Lock the workstation.

Those operations do not require streaming a desktop. They need service discovery, an authenticated control channel, and a small command set.

Heimdall targets that shape of problem: **service discovery + authenticated control** for operational tasks.

## Architecture

Two components:

1. **Android application** — the client. Written in Kotlin.
2. **Heimdall daemon** — a Go agent on the host. It advertises itself, authenticates sessions, and executes capabilities.

```text
Android
   |
   | mDNS
   v
Heimdall Daemon
   |
   +-- System
   +-- Processes
   +-- Network
   +-- Security
   +-- Power
```

The daemon is designed around capabilities rather than UI operations:

```text
system
process
power
network
storage
files
display
audio
```

Each capability can expose several commands. The client stays platform-agnostic; the daemon translates a command such as `power.shutdown` into the appropriate host operation.

This split also leaves room for other host implementations later. The protocol can remain the same while a platform-specific agent changes.

## Discovery

The first problem was finding computers on the local network without asking the user for an IP address. DHCP moves addresses. Manual configuration makes the product worse.

The daemon advertises itself. The phone searches for agents.

<HeimdallDiscovery />

Each discovered computer provides information such as:

```json
{
  "id": "01J...",
  "name": "desktop",
  "platform": "linux",
  "version": "0.1.0",
  "port": 48271
}
```

Discovery answers one question: _which agents are available?_

The control protocol answers a different question: _what can I do with this host?_

Those responsibilities stay separate so either side can evolve independently. Discovery stays lightweight. It does not carry sensitive control data.

## Protocol

Control uses request/response messages over TCP rather than a REST surface. The first version was JSON, which was replaced by a binary protocol once it became clear that a length-prefixed envelope was required regardless.

Every message is a fixed 18-byte header followed by a payload of up to 16 MiB:

```text
+---------+----+----+---------+-------------------+---------------------------------------+
|  Magic  |Ver |Flg |  Type   |  Payload Length   |              Request ID               |
+---------+----+----+---------+-------------------+---------------------------------------+
|<- 2B -->|1B  |1B  |<- 2B -->|<------ 4B ------->|<---------------- 8B ----------------->|
```

All multi-byte fields are big-endian and encoded explicitly, field by field. The 64-bit request ID lets several operations be in flight at once without depending on ordering, since responses are correlated by ID rather than by position in the stream.

The flags byte carries the message class. Exactly one of `REQUEST`, `RESPONSE`, or `EVENT` must be set, and `ERROR` may only accompany a response. Events use request ID `0`, which is reserved for messages that answer to nothing.

Message types are 16-bit, with the high byte identifying the domain:

```text
0x0100 - 0x01FF   system
0x0200 - 0x02FF   process
0x0300 - 0x03FF   network
0x0500 - 0x05FF   power
```

Live metrics do not require polling. The daemon publishes them as events on the same connection, which is the session shape a live dashboard needs: requests for actions, events for changing state.

The frame layer ships as [`heimdallp`](https://github.com/gabriel-kimutai), a standalone Go library with its own specification. Payload encoding above the frame is deliberately still open. There is a longer write-up of the design in [Eighteen bytes in front of every message](/writing/designing-a-binary-protocol/).

## Security

Remote management needs more than an open LAN socket. The intended model is pairing with cryptographic identity, then authenticated and encrypted control sessions.

The daemon should have its own cryptographic identity. During initial pairing, the Android application and computer establish trust. After pairing, each side can authenticate the other. Subsequent connections use the established identity instead of asking the user to re-enter credentials.

<HeimdallSecurity />

Discovery remains a locator. Authentication happens when establishing the control connection. Management actions require established trust — pairing before privilege.

## Implementation

**Daemon in Go** for networking, concurrency, and a deployable Linux service, including systemd packaging concerns.

**Client in Kotlin/Android** for a native management UI.

**Capability-oriented API** so the phone stays platform-agnostic.

**mDNS for discovery** to avoid manual addressing on DHCP networks.

The first version focuses on a small, useful surface rather than attempting to build everything at once:

```text
System
 ├─ System information
 ├─ CPU usage
 ├─ Memory usage
 └─ Disk usage
Processes
 ├─ List processes
 ├─ Inspect process
 └─ Terminate process
Power
 ├─ Shutdown
 ├─ Restart
 ├─ Sleep
 └─ Lock
```

Additional capabilities can layer on without rewriting the client/daemon boundary. Possible later work includes network monitoring, file management, service management, and terminal access — none of that is claimed as shipped.

## Challenges

- Keeping discovery simple while keeping control secure
- Designing a protocol that supports concurrent requests and streamed events
- Translating one command set across platform-specific implementations
- Shipping a daemon that fits naturally on Linux (including systemd) without becoming a remote-desktop stack

## Results

Heimdall is in active development. The core architecture is taking shape around one principle: a computer should be manageable from a screen you already have, without streaming a desktop.

The first milestone is simple: discover a computer, establish a trusted connection, and perform a small number of useful operations. Everything else can build on that foundation.
